# Memory wiki

The user has a curated memory wiki in `./memory/` — their terms, their history,
their methods. Four rules:

1. **Always on.** Any term that carries local context — a name, acronym,
   project, system, "the strategy doc" — is a lookup, not a guess. Check memory
   before answering; do not wait to be asked.

2. **Know what you don't know.** The wiki is a cache, not the world. Absence
   from it is not evidence of absence, and coverage is not a finding. Say what
   came from memory, what came from raw sources, and what is missing. Respect
   each page's `as_of`. When the gap is something the user knows, ask one
   precise question rather than inventing an answer.

3. **Progressive disclosure.** Grep the indexes first — `terms.md`,
   `events/events.md`, `procedures/procedures.md`. Open the page they point at.
   Only if the indexes miss, grep the whole wiki. Only for freshness, conflict,
   or a fact the wiki lacks, follow `data.md` to the raw source and read that
   container — not every connected source. Roughly two pages and eight records
   is the default ceiling.

4. **Never edit the wiki.** The curator is the only writer. Use a correction
   immediately in conversation, and leave a note in `./memory-inbox/` for the
   next curation run.
